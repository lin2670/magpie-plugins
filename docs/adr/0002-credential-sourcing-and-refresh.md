# 登录态维护：复用优先，三级来源（桌面端凭据 / agent2api 导入 / 手动）

---
status: accepted
date: 2026-10-14
---

四家服务都要以用户自己的登录态访问上游，各家续期机制不一（小浣熊、Accio 有 refresh token 可自动续期；CatPaw、Loomy 无续期接口）。我们决定**不重实现登录流程**，按三级来源取得与维护凭据：① 有桌面端凭据可读的（妙手）由插件直接读取、随桌面端登录自动刷新；② 其余服务（小浣熊 / Accio / Loomy）先从参照实现 agent2api 的现有账号一次性导入；③ 兜底走 magpie 的手动登录入口。能自动续期的由插件在凭据层自动续期；无续期的（CatPaw / Loomy）过期后按 ①②③ 重新取得。账号按 magpie 惯例支持多账号，每日任务逐账号执行。

## Considered Options

- **在插件里重新实现各家登录（扫码 / 验证码 / OAuth）**：工作量大、易被上游改版打断，且多数服务没有面向第三方的登录开放接口。
- **只支持手动粘贴 token**：最简，但可维护性差（token 短期过期、用户操作频繁）。

## 修订（2026-10-15）：Loomy / AutoClaw 例外，重实现手机验证码登录

status 不变（accepted）。**Loomy 与 AutoClaw 国内版两家重实现了手机验证码登录**，作为 ①②③ 之外的第四来源（`agent-send-code` → `agent-login` / `checkCode`，协议见侦察笔记），与导入、手动粘贴并列出现在 magpie 登录方式里。

- **动机**：这两家的 session 短（Loomy 14 天、AutoClaw JWT 数小时），agent2api 里又只有一份账号——导入与手动粘贴都救不了「长期使用」，只有插件自己能登录才能让多账号长期自持；且两家登录协议都是**纯短信验证码两步**（无扫码 / 滑块 / OAuth），是四家里最容易稳定复刻的形态。
- **边界（仍是红线）**：只做"发验证码 + 验证码换 session"这两步，不碰风控（遇验证码图/滑块走 `captcha` 通道）；其他家（小浣熊 / CatPaw / 任何 OAuth 流程）仍按原三级来源，不重实现。
- **代价**：验证码登录路径要随上游改版维护（与被否选项里指出的风险相同，接受此代价换长期自持）。

## Consequences

- 插件需提供凭据的导入 / 重读入口（本地文件读取 + 一次性导入），而非只依赖交互式登录。
- 妙手以"随桌面端登录自动刷新"为常态（重开妙手即自愈）；Loomy 无续期接口是已知短板，过期只能重登后重新导入——**修订后 Loomy 可直接在插件里重新短信登录，此短板缓解**。
- 出网代理池（参照实现内置）v1 不移植；先用系统网络与 magpie 既有代理机制。
- 多账号 + 逐账号每日任务为默认行为，无需额外开关。
